# 108 · The picture checks run on a photograph you choose

## Context

**The goal.** The test page takes a photograph the reader chooses, runs the same picture checks on it, and prints a report that names the file and its camera beside the figures, so a session can run the same checks on the same file from the folders the owner shared and compare the statistics.

Where it stands. The test page's "Picture checks" section (record 106's first stage with the 2.71 additions, the progress line, the time per stage and one decode and one build per press, on staging as 2.71) runs three checks three times each on one fixed photograph: the bundled practice file under `public/examples/`, fetched by the page, decoded once and drawn through one drawing surface. That file is a hand-written DNG with no EXIF (record 082), so the app opens it with no camera, no lens and no lens correction. The checks are relative inside one run on one chip: a look applied twice, a press at a slider's own value, the direction of Temperature. They set no band. The question that prompted this record is whether, with the practice file standing in for the owner's camera, the checks were testing the wrong data and later work was being built on it. Read against what the checks assert, the relative ones (zero pixels move, a statistic rises) hold on any photograph and are not wrong; what they cannot do is say anything about the picture the owner's camera makes, and any absolute band written from them would be a band from a frame the camera never made. Record 106 already refuses a band before a device prints the figures; this record closes the other half, which frame the figures come from.

What decides it. The doctrine's section on test pages says a test page is read-only with respect to the reader's work and opens nothing of theirs. A file the reader picks is handed to the page by the reader's own act, in the page, and nothing leaves the device; the page reads it into memory the way the editor does and writes nothing back. That reading of the clause is this record's, and the clause's own words ("opens nothing of theirs") are stricter than it; whether the doctrine's sentence should say "nothing the reader has not handed it" is the hub's and the owner's to settle, and this record builds nothing until it is. That was settled on 4 November 2026: the clause is to say the page opens nothing the reader has not handed it, the wording lands in the hub with its next release, and this record's build plan follows that release.

## Looked up

- **MDN, "Using files from web applications"** (fetched). Choosing a file through an input element only gives the page access to a `File`; nothing is uploaded unless the page's own code sends it. A `File` exposes `name`, `size` and `type` and no path. Bytes are read with `FileReader`; the page does not document `arrayBuffer()`, size limits or permission prompts, which were not read.
- **A search on reading a local file without uploading it** (summaries only, no page opened beyond the one above): the same pattern, a change handler on the input, then a read in the browser; the real path is hidden behind a placeholder. Nothing found contradicts the MDN page.
- **The doctrine, section 7j** (read whole): read-only with respect to the reader's work, one button, text that copies with the app version and device facts, three runs and a median, suspicious of its own instrument. Its clause on opening nothing of the reader's is the tension named in Context.
- **The app's own code** (read): `readExifSubset` in `src/exif.ts` takes the whole file or its head and returns make, model, lens, focal length, aperture, exposure time and ISO, or null; the editor reads a file's EXIF with it at open (`readOpenExif`, `exifOf` in `src/main.ts`) and an unreadable header is an unmatched photograph, never a failure. The test page's picture checks fetch the bundled practice file and build an `ImportedFile` from its bytes (`pictureChecks` in `src/debug.ts`); a reader's file can be given to the same path in place of that fetch.
- **`tools/owner-images.mjs`** (header read): the one door to the owner's shared photographs; `--list`, `--fetch NAME`, and `resolve` refuse a practice file and any name the index does not carry. A session fetches the same file the reader picked by its name from that index.
- **Not read:** how the iPad's installed app presents the file picker (the photo library against the Files app, and whether it hands back the original or a re-encoded copy; this decides whether the same file is the same bytes); the size of a camera raw against the page's memory on the 4-core iPad; any source on a browser changing a file's bytes on pick.

## Weighed against

- **Record 106**, the page and its section: this adds a way into that section, not a second section, and keeps every check, planted pair, expectation and the readback test of the planted colour as they are.
- **Record 082**, the practice files carry what a reader's file carries: that record gives the bundled frames a camera; this reads the reader's own. A practice file given borrowed camera data is still not the reader's photograph, so the two do not substitute.
- **Record 107**, the walks on a machine with a chip: it runs the walks as they are on a PC, and reaches the owner's photographs through `tools/owner-images.mjs` on that machine; this reaches the iPad's WebKit and Apple chip, which it cannot. Neither covers the other.
- **The doctrine's read-only clause**, in Context.
- **The app's rule on the owner's files:** calibration and every render a record reports use only the files in `tools/owner-images.json`. A reader who picks a file is not bound by that, but a session comparing the figures is: it fetches the named file through the tool and runs nothing on a file the index does not name.
- **Done before on this ground:** the page opens nothing of the reader's at present; the editor opens the reader's files and reads their EXIF; no instrument has taken a reader's file and printed figures beside the camera.

## Options

1. **A control in the picture checks section that takes one photograph the reader picks, runs the three checks on it in place of the practice file, and prints the file's name, its camera and lens from its EXIF, its pixel size and the figures. Chosen.** The report names the file and the camera first, then the renderer string and the app version as now, then the checks; the planted colour and the planted pairs run first as now, so a perturbed readback stops the run before any figure is printed. The comparison is made by a session, not by the page: the session fetches the same file by name through `tools/owner-images.mjs`, opens it in the same pipeline on its own renderer, and sets the counts the page prints (pixels moved, over 8 and over 24 of 255, the Temperature statistic) beside the report, a software renderer being named as such in both. It compares statistics and never a hash. What it costs: a surface change on an existing page, which owes the accessibility walk, the control walk's inventory, a line in the manual coverage and a device pass; a raw from the camera is decoded for the press, which on the 4-core iPad is more than the practice file (the stage times the page now prints will show it); the page must handle a file it cannot decode with words and a way forward; it needs a stated answer on whether the file is read as the original bytes on the iPad, which is not read; and a reader who picks a file puts that file's name and camera into a report the reader then chooses whether to paste, so the report says so beside the copy button.
2. **Record 106's kept second stage, the editor in a same-origin frame with script events.** Kept, not chosen: it would reach the checks that need a control's move, but it depends on the editor's element ids and on script events that are not a finger's, and it does not by itself give the report the file and camera.
3. **A reader pastes or sends the photograph itself into a chat for a session to compare.** Rejected below.
4. **Leave the checks on the practice file.** The standing position; it leaves the question that prompted this record open, and any band set from the practice file's figures would be a band from a frame no camera of the owner's made.

## Rejected

- **Pasting a picture into a chat for a session to read.** A session cannot read pixels from a pasted picture reliably: the chat re-encodes it, drops a raw's data and carries no EXIF, so it would compare an impression, which is the work the doctrine says a session must not hand to the owner, and it would send the owner's photograph through a channel the page's rule says nothing leaves by.
- **A stored reference result per device, filled in from the reader's file.** It multiplies by every device, goes stale at every look change, and records a result for a file the repository must then carry or name; record 106 rejected the same shape.
- **A hash across devices.** Record 106's measurement stands: two Apple chips gave different hashes and the same statistics, and a hash says only identical or not.
- **Giving the practice frame the reader's camera data.** That is record 082's ground and it does not make the frame the reader's photograph; the lens correction would then be measured on a different file.
- **Setting any band from the practice frame's figures meanwhile.** A band is set only from a report a device printed on a frame the owner's camera made; this record is the route to that report, and record 106 now says so.

## Rank

Ninth, directly under 106 and above the first look change with work to build. The dependency test is what the items ranked above it would have to redo and what the items below it wait on. Nothing above it waits on it: three are built and need only their device pass, three have nothing left to build, 107 changes no app code and does not need it, and 106's own instrument is what this one grows from, so it sits below 106 and cannot be built before it. The look changes below it are accepted by pictures, and the absolute band any of them might need can be set only from a report on a frame the owner's camera made; with the checks fixed on the practice file the first such band would be written from the wrong frame and then moved, so whatever is tuned against it would be tuned twice. That is the dependency, and it puts this ahead of them. It is behind 106 because it needs 106's section to exist. The rank is the dependency's, not the defect's.

## Built

Built on staging as 2.72 by the plan of 6 November 2026 (step 305). The test page's Picture checks section gains a file input with a label, `#dPicFile` in `debug.html` driven by `src/debug.ts`. A picked file is read into memory on the page, built into an `ImportedFile` with `sniff`, and given to `loadSubject`, which is the one place the press obtains its photograph: the picked file decoded once off the page's thread when one was picked and it decodes, else the practice file fetched and decoded as before. The three checks run on it in place of the practice file, with their planted colour, planted pairs, expectations and figures as they were. A row at the head of the report names the file, its kind, its pixel size and, from `readExifSubset`, its camera and lens and the focal length, aperture, exposure time and ISO where the file carries them, or says no camera was read. A file the page cannot decode gets a row in the not-measured words saying why, and the practice file is used. A note under the input and one beside the copy button say that the file's name and camera are in the copy and that nothing is uploaded or saved. The stage rows name the picked photograph where the practice photograph was named. How the iPad's picker hands a raw to the page is not read here; the owner's press answers it.
