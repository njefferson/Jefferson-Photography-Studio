# 107 · The picture walks run on a machine with a graphics chip

## Context

**The goal.** The picture walks run as they are on a machine with a graphics chip and real browsers, by one command, with the owner's only act the opening of a session there.

Where it stands. Twenty-one of the app's walks read the drawn picture and are not run in the container, which draws through a software renderer that is neither the chip nor the browser a reader uses (the app's instructions, the bullet that opens "Which walks run where"). They are the walks that can say whether a look change or a control's move changed the picture, so a look is checked by a reader's eyes on a device or not at all. The temperature walk alone takes 56 to 74 minutes under software drawing. The machine at hand is a PC that runs Firefox on Windows 10 with a GeForce GTX 980 through Direct3D 11 and twelve cores, reports a maximum texture of 16384 pixels and built the editor's picture code in 2.8 seconds; the sessions the walks run in start on a Linux container.

What stands in the way, read from the walks. Every walk that launches a browser names the executable `/opt/pw-browsers/chromium`, and all but a handful pass `--use-gl=swiftshader` and `--enable-unsafe-swiftshader`. The container's paths (the checkout, the browser folder, a session scratchpad) occur 106 times across 57 files under `tools/`, and some walks import `playwright-core` by an absolute path into the checkout (Q-JPS-131). Most walks' usage lines start a static server with `python3 -m http.server` on port 8131. And a headless Chromium draws in software by default: as its source reads, software rendering is configured unless the command line already carries a switch for the GL implementation, for the ANGLE backend or for the GPU, so the walks' own `--use-gl=swiftshader` pins the software renderer on any machine, a chip included.

What decides it. A chip machine measures things the container cannot see, and the app's own notes name them: the cost of the Direct3D compiler on the picture code (record 071 measured 42 to 47 seconds on the PC, which the container "would never notice"), the browser's limit on graphics contexts (Firefox on the PC would not make a sixth), the true texture limit, and the per-chip residue in the noise reduction and sharpening (a software renderer and a GTX 1650 read 492 and 559 pixels over 24 of 255 there). It does not measure the iPad: Playwright's WebKit is built from WebKit's main branch and is not the iPad's Safari on an Apple chip. And for the colour-only part of the pipeline the container already agreed to the digit with the GTX 1650, so what is gained there is smaller than the instruction's single sentence suggests. The record asks which way of reaching a chip is worth building, and in what order the walks' own launch lines have to change.

## Looked up

- **chromium/chromium**, `headless/lib/headless_content_main_delegate.cc` (listing read, file read, as the fetch tool reported it). "Use software rendering by default, but don't mess with gl and angle switches if user is overriding them"; the software configuration is applied only when none of the GL-implementation switch, the ANGLE-backend switch and the enable-gpu switch is present. `ui/gl/gl_switches.cc`: the ANGLE-backend switch selects among default, d3d9 (legacy, ES2 only), d3d11 (ES2 and ES3), warp (D3D11 with software rasterisation), gl and gles; the GL-implementation switch lists desktop, egl ("Windows default - actually ANGLE") and swiftshader; a separate switch is "Allow usage of SwiftShader for WebGL".
- **microsoft/playwright**, `packages/playwright-core/src/server/chromium/chromiumSwitches.ts` (listing read, file read, as reported). Playwright's default switches include the unsafe-SwiftShader switch and `force-color-profile=srgb`, and none about the GPU, ANGLE or GL; nothing is gated on headless. `docs/src/browsers.md`: a regular Chromium build for headed runs and a separate headless shell for headless ones; "You can opt into the new headless mode by using 'chromium' channel"; each Playwright version needs specific browser versions and the install command is run again after an update; browsers install by name (`npx playwright install firefox`); the Windows store is under the user profile's AppData Local `ms-playwright` folder and `PLAYWRIGHT_BROWSERS_PATH` moves it; Playwright's Firefox "relies on patches"; the page has nothing on GPUs and nothing on WSL. `docs/src/api/params.md`: custom arguments are "at your own risk, as some of them may break Playwright functionality"; the option that drops Playwright's own switches is "Dangerous option; use with care"; a browser executable other than the bundled one is "use at your own risk".
- **GitHub issues found by search** (two opened, anecdotal, not documentation). A luma.gl issue reports headless Chromium forcing software drawing until the enable-gpu switch was given, and only with a display; another report found one combination of GL and ANGLE switches with the GPU-blocklist override that reached an NVIDIA card in new headless mode with no display; a third (not opened) reports the SwiftShader GL choice no longer valid on newer Chrome builds. The advice repeated throughout the results: a working WebGL context is not proof of a chip, so read the unmasked renderer string or `chrome://gpu` and refuse a software renderer.
- **Firefox through Playwright.** No source read says whether headless Firefox on Windows draws WebGL on the chip; a search summary points to an old Mozilla bug on headless WebGL and to a Playwright Firefox build setting that permits software WebGL. The PC's own reports are a headed Firefox. Not settled.
- **A Linux layer on Windows** (search summaries only; Microsoft's DirectX post did not resolve, and Mesa's two driver documents answered 404 on the paths tried). The host chip reaches a WSL 2 guest by GPU paravirtualisation; OpenGL comes through Mesa's D3D12 driver and Vulkan through its dzn driver, with a recent display driver on the host. The one WSLg issue found reports Mesa falling back to llvmpipe on a hybrid-graphics laptop and Chrome crashing unless acceleration was disabled. No source found confirms Chromium's WebGL on the chip in WSL 2.
- **The app's own tools** (read): `tools/walk-all.mjs` runs every `*-walk.mjs` as its own process, one at a time, with `--port` and `--only`, refuses a stale `dist` through `tools/fresh-dist.mjs`, and lets one walk bring its own server; no walk uses a Chromium-only protocol session (a search for them found none); `tools/owner-images.mjs` fetches the shared photographs by name for the walks that need a camera JPEG; the walks' browser lines are in the files themselves.
- **Not read:** whether the other walks use anything that Playwright's Firefox lacks; how `tools/owner-images.mjs` fetches on a machine with no connector; Chromium's own documents on headless GPU use (developer.chrome.com did not resolve); Mesa's driver documents; any measurement of a walk on the PC. Hosts that did not resolve: developer.chrome.com, devblogs.microsoft.com, chromium.googlesource.com and bugs.webkit.org.

## Options

1. **A native Windows run on the PC: the walks' browser, flags and import come from one small launch module, Chromium headed with the chip chosen and Firefox headed, one command. Chosen.** The module holds what is now repeated in 57 files: the browser's path (Playwright's own install on that machine, found by Playwright and not named), the flags (none that name a software renderer; the chip is left to the browser's default on Windows, which the ANGLE switch's own comment calls the default, and the ANGLE backend d3d11 is named only if the renderer check below shows a software fallback), the `playwright-core` import and the static server, so `walk-all` runs every walk by one command with the machine named once. The first check of every run reads the unmasked renderer string in the page and refuses a software renderer by name (SwiftShader, WARP, llvmpipe), so a run that fell back to software cannot print a verdict; that check is made to fail once by a run with the software flags put back. Each walk is run once against its plant on the machine, because a bar set under software drawing may be too tight or too loose on a chip, and none is loosened to go green. Browsers are installed by `npx playwright install` at one Playwright version written in the launch module (the sweep of 31 October used playwright-core 1.56.1), because the lockfile does not name the harness's packages (Q-JPS-158). What it measures that the container cannot: the Direct3D compile of the picture code, the context limit, the true texture limit, the chip's rounding in the two neighbourhood operators, and the real pace of the slow walks. What it does not: the iPad (Playwright's WebKit is not the iPad's Safari, and record 106 is the instrument that reaches it) and any browser the PC does not have. What it costs: a mechanical change to 57 files that must leave every walk as strict as it was; a decision on what runs on the PC by default (the 33 structural walks already run in the container, so the 21 picture walks are the new ground); Firefox's differences from Chromium for each walk are found by running them; and the owner opens a session on that machine, which is the one act no session can do.
2. **The same run headless, in new headless mode with the chip's backend named. Kept.** Saves the window and lets a run go unattended. The sources read are reports and not documentation, and the renderer check above is what would prove it, so it is a variant to try after the headed run works, not the first.
3. **The walks as they are, inside a Linux layer on the PC.** Rejected below.
4. **Leave the picture walks to the device, as now.** The standing position; it meets none of the goal.

## Rejected

- **A Linux layer on Windows (WSL 2).** Its one advantage is that the walks' Linux paths already fit, and those are the paths to remove in any case. No source read shows Chromium's WebGL on the chip there, the one report found fell back to the software renderer, and the graphics stack is Mesa over Direct3D 12 where a reader's Windows browser goes through ANGLE over Direct3D 11, so a pass there would measure a stack no reader uses.
- **Making the container draw on a chip.** It has none; the container's graphics are the premise of the record.
- **Editing each walk's own flags in place.** It is the same 106 paths repeated, one launch module being the only change that cannot drift, and the shape record 083's gate wants.
- **Loosening a walk's bar to make it pass on the chip.** A walk changes only to stay as strict or grow stricter; a bar that the chip cannot meet is a finding about the chip or the bar, written down, and not a loosening.
- **Taking a green run on the PC as proof for the iPad.** Different engine, different chip: the app's own measurement found the systematic difference tracking the browser and not the chip, and Apple's engine reads closer to the computed frame than Chromium's does.
