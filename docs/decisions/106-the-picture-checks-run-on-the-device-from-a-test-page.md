# 106 · The picture checks run on the device, from a test page

## Context

**The goal.** The checks that read the picture run on the device's own graphics chip in minutes, from one button, and print a report that copies, which the doctrine's section on test pages already asks for.

Where it stands. Twenty-one walks read the drawn picture (aerochrome, aim, camera-jpeg-sky, conversion, double-tap, fix-brush, fullview-mask, grade-controls, heal-source, lens-order, look-roundtrip, mask-fix, mask-slots, mask-truth, opens-as-shot, quicklook-speed, rotation, sky-stage, slider-own-value, straighten-line and temperature). The container draws through a software renderer, which is neither the chip nor the browser a reader uses, so these walks are not run there and a look change is checked by the reader's eyes on a device or not at all. The temperature walk alone takes 56 to 74 minutes under software drawing. The devices that answer are two: an iPad, which runs WebKit on an Apple chip from the home screen, and a PC, which runs Firefox on Windows 10 with a GeForce GTX 980 through Direct3D 11 and twelve cores, reports a maximum texture of 16384 pixels and built the editor's picture code in 2.8 seconds.

A test page exists and already runs on the device: `debug.html`, driven by `src/debug.ts`, behind the version number. It measures graphics draw and readback, the build of the picture code row by row, decode on the main thread against a worker, storage, texture and drawing-surface limits, cores, and a comparison of a drawn export with a computed one on a fixed crop of a bundled practice photograph. It reads no walk's check: nothing in it opens the editor, presses a control or asks whether a picture is right. This record asks what the page should run so the picture checks have an instrument on the device, what each check is compared with, and how the result travels.

What decides it, from the app's own notes and the walks' headers. First, most of what the picture walks assert is relative inside one run on one chip: a patch statistic rises after a move, zero pixels move after a press at a slider's own value, a round trip through a look draws the same frame. Those need no stored picture and are not changed by a chip that rounds differently, because both sides of the comparison are drawn by the same chip. Second, what does cross chips is a statistic and never a hash: two Apple chips drew exports whose byte hashes differed while five difference statistics agreed to the digit, and the colour-only frame read the same on a software renderer and on a GTX 1650 through Direct3D 11, differing only where the noise reduction and sharpening ran (492 against 559 pixels over 24 levels of 255). Third, a page cannot press the editor's controls the way the walks do, with a pointer; it can render the pipeline with two parameter sets and read the pixels.

## Looked up

- **web-platform-tests/wpt**, `docs/writing-tests/reftests.md` (listing read, file read). Fuzzy matching is a declared pair: the largest per-channel difference at any pixel and the count of pixels that may differ, both required, ranges allowed, inclusive. It exists because "a test may have subtle differences in rendering compared to the reference due to, e.g., anti-aliasing". The page is silent on differences between platforms or graphics hardware. Its runner (`tools/wptrunner/wptrunner/executors/base.py`, as the fetch tool reported the code) passes on a hash match, else on the two numbers; it writes the measured numbers to its log and not into the failure message, which is the reverse of what a report that has to be pasted back needs.
- **microsoft/playwright**, `docs/src/test-snapshots-js.md`. Rendering "can vary based on the host OS, version, settings, hardware, power source"; snapshots are stored per browser and platform; the comparison is the pixelmatch library, with a threshold on the per-pixel perceived difference (default 0.2) and a count of pixels that may differ (unset by default).
- **mapbox/pixelmatch**, README. Compares in the OKLab colour space with the HyAB distance, threshold 0.1 by default, anti-aliased pixels detected and ignored unless asked; returns the number of mismatched pixels; a window option returns the highest count in any window, because scattered noise rarely fills one and a real regression does.
- **chromium/chromium**, `content/test/gpu/gpu_tests` (listing read, files read). Its pixel tests use an exact algorithm, a fuzzy one (a count of pixels that may differ and a per-channel or summed delta) and one that blacks out edges first; entries are commented as rounding error with a per-channel delta of 1, one phone "tends to produce images with all colors shifted by a small amount", the sRGB tests "create a large number (~15,000) of pixels with difference ~3"; parameters are "determined using the automated optimization script". `docs/gpu/gpu_testing.md` says the GPU bots run tests "whose results are likely to vary between graphics card vendors" and that "GPU-specific results are maintained" where necessary. No comment attributes a tolerance to a chip by name.
- **Search summaries only, no page opened:** GLSL precision qualifiers set a minimum range and precision, and an implementation may use more; Firefox's resistFingerprinting randomises canvas reads unless a canvas permission is granted; Safari's fingerprinting protection adds noise to 2D canvas and WebGL readback in private browsing from Safari 17 and, by one source, in every mode from Safari 26. A page that reads its own picture back can be handed perturbed pixels in those modes; no source read says which modes the iPad's installed app runs in.
- **The app's own record** (NOTES.md, the September 2026 sections on three graphics chips, on the counts of pixels over 8 and 24, and on the drawn export), read: the figures above, and the file's own conclusion that a fingerprint answers identical-or-not and says nothing of how far, so the instrument counts the pixels over 8 and over 24 of 255. The systematic difference between a drawn and a computed frame tracked the browser engine and not the chip.
- **The doctrine, section 7j** (read whole): a test page is read-only with respect to the reader's work, behind the version number, one button, then text that copies with the app version and the device facts; three runs and a median with the individual numbers; measured the way the app works; suspicious of its own instrument.
- **Not read:** the ES 3.0 text on invariance; Safari's or Firefox's own documents on canvas readback; a metric tuned for photographs (a structural-similarity or colour-difference study); the other thirteen picture walks' headers (eight were read, so what is said of "most" is of those eight). Hosts that did not resolve: chromium.googlesource.com (the pixel test source, read from the GitHub mirror instead), bugs.webkit.org (the WebKit bug on its privacy protections and canvas readback) and, from step 264, web-platform-tests.org and playwright.dev (Q-JPS-170; the same documents read from their repositories).

## Options

1. **A section of the test page that renders the app's own pipeline with fixed parameters on the bundled practice photograph, reads the pixels back, and prints each named check with its measured numbers and a verdict. Chosen.** Where the expectations live: nowhere, wherever the walk's assertion is relative to a second render made in the same run (the look round trip, a press at a slider's own value, the Temperature direction as two parameter sets); and, for the few absolute ones, as a band written in digits beside the check in `src/debug.ts` with the measured figures printed next to it, so a band is tuned from data and never guessed (the reftest runner's shape, with the measured values kept). What is compared: the largest per-channel difference and the count of pixels over 8 and over 24 of 255, which are the app's own two bands and the reftest pair; a byte hash only between two renders of one run on one chip, never between devices; a patch statistic where the walk uses one. How the report copies: one button; three runs and a median with every run printed; the app version and the device facts; the renderer string on the first line, with a software renderer named as such and the report saying so; each check's planted pair first, with its known figure, so a check that cannot fail is seen not failing; a check that cannot run says why in the page's not-measured words. A planted known colour is drawn and read back before any check, and must read exactly: if the browser perturbs readback, the report says so and runs no check, which is what the fingerprinting protections would otherwise turn into false verdicts. What it costs: it covers the checks that can be phrased as render-and-read, which from the eight headers read are the round trip, the own-value press and the Temperature direction, and not the ones that need a pointer (the straighten line saves a before and an after for the eye, and fix-brush and the mask strokes were not read), and which assertions can be phrased that way is read walk by walk by the build plan; it is a surface change on an existing page, which owes the accessibility walk, the control walk's inventory and a line in the manual coverage; its cost on the device is the practice photograph's decode and a computed export of 2.7 to 4.3 seconds each on the devices measured, so a handful of checks fits in minutes; and a verdict printed on the iPad is read by a hand pasting it back.
2. **Run the editor in a same-origin frame on the page and press its controls with script events. Kept.** It would reach the checks whose assertion is a control's move (the Temperature drag, the press at a slider's own value) as the walks do. It is kept for the second stage because it makes the page depend on the editor's element ids, script events are not a finger's (the iPad's touch events are the reason the pointer walks exist), and nothing yet says the editor can be driven that way on the iPad.
3. **Compare against a stored picture per device and browser.** Rejected below.
4. **Leave the device pass to the hand.** The standing position, and the one the doctrine asks a session to replace.

## Rejected

- **A stored reference picture per browser and platform, compared by a perceptual metric** (Playwright's snapshots; Chromium's Gold with chip-specific results). It multiplies by every device and browser the app is read on, each file a photograph the repository would carry (the practice files carry no EXIF and the shared files are not for copying into the tree), it goes stale at every look change and needs approving again, and Chromium keeps its own through an external service the app does not have. The app's own measurements show chips of one family differing by a handful of pixels, so a stored picture would be matched by a band anyway, which is option 1's band without the picture.
- **A byte hash across devices.** It answers identical-or-not and says nothing of how far; the app's own September measurement found two Apple chips with different hashes and identical statistics, and NOTES.md's earlier sentence that three chips drew three different photographs was corrected there for exactly this reason.
- **Porting the twenty-one walks into the page.** They are written against Playwright's page and pointer interface, so the port is a rewrite of each; the checks that matter are the assertions, which option 1 phrases once.
- **Trusting what a canvas reads back.** A browser may add noise to the read in some modes (search summaries, not opened); the planted colour at the start of the run is how the page finds out instead of assuming.
- **A tolerance written down before a device has printed the figures.** The bands are set from the first reports the page prints, as the reftest runner's logged values and the app's own counts were.

## Measured

Read from the app's own notes (NOTES.md, September 2026 sections), not run in step 270. A frame drawn from the full-resolution source took 16 to 17 ms on the 8-core iPad, 32 to 44 ms on the 4-core iPad and 10 to 13 ms on the desktop. The computed export of a two-megapixel crop took 2.7 s on the 4-core iPad, 4.3 s on the 8-core iPad and 4.1 s on the desktop, the drawn one 0.6 s, 1.1 s and 0.9 s. With the noise reduction and sharpening off, the drawn frame against the computed one read average 0.21 of 255, worst 74, 450 pixels over 8 and 134 over 24 on both a software renderer and a GTX 1650 through Direct3D 11, and average 0.19, worst 47, 152 over 8 and 31 over 24 on two different Apple chips; with the operators on, the software renderer and the GTX 1650 read 492 and 559 over 24. A byte hash over the drawn frame differed on every chip; the statistics did not. The temperature walk takes 56 to 74 minutes under software drawing.

The planted colour, drawn as 200, 100, 50, read back as 187, 105, 62 for the expected 187, 105, 62 on all three, 0 of 1024 pixels off. The look applied twice and the press at a slider's own value each moved 0 of 800080 pixels, worst 0, in all three runs, on all three. Temperature's red over blue, swap on then swap off: the iPad's installed app on its Apple GPU read 0.3478 to 0.3820 and 2.7134 to 3.1643; Firefox 159 on Windows drawing through ANGLE on the GeForce GTX 980 with Direct3D 11 read 0.3475 to 0.3816 and 2.7154 to 3.1669; the container's software renderer (SwiftShader) read 0.3478 to 0.3820 and 2.7134 to 3.1642. ## Built

First stage, built on staging: the test page `debug.html` gains a "Picture checks" section with one button and one copy button, in `src/debug.ts`. The button prints the renderer string first and names a software renderer as such, draws a planted colour through `drawFrame` and reads it back (a mismatch of even one level stops every check), tries the comparator and the patch reader on made pairs with known figures, then runs three checks three times each and prints the median with every run:

- A look applied twice draws the same photograph: the same look's numbers applied from the opening baseline and drawn twice; expects zero in the largest difference and in the counts over 8 and over 24.
- A press at a slider's own value moves nothing: exposure and gains read back through the slider's grid; expects zero pixels moved.
- A warmer white raises the patch's red over blue, with the red and blue swap on and off, the statistic the Temperature walk reads; only the direction is asked.

Each verdict is printed beside the measured numbers and what the check expects of them. The planted move (the exposure raised a quarter) is drawn in every run so each frame check is seen to read a difference when there is one.

Not yet phrased, eighteen: aerochrome, aim, camera-jpeg-sky, conversion, double-tap, fix-brush, fullview-mask, grade-controls, heal-source, lens-order, mask-fix, mask-slots, mask-truth, opens-as-shot, quicklook-speed, rotation, sky-stage and straighten-line. Each needs a pointer, the editor's own controls, a mask the drawn path does not cover, a shared owner photograph or a timing, so none is two renders read back in one run. They wait for the second stage, the editor in a frame.

Every band is unset: the checks expect zero or a direction and write no tolerance, and an absolute band is set only from a report a device has printed. A band is set only from a report a device printed on a frame the owner's camera made, which record 108 is the route to, and never from the bundled practice frame's figures.

Second stage of the page, built on staging as 2.71 (the plan of 3 November, step 288): the press says where it is, times each stage and builds once. One line below the buttons, in a polite live region present from parse, names the check, the run, the frame and the stage and the whole seconds so far, and ends on the whole time; it changes at each frame and not on a timer, so a screen reader is not read to every second. Every stage is timed with the page's own clock and printed beside it in the section and in the copy: the practice file's read, the practice photograph's decode, the picture code's build, the planted colour, the photograph's pixel build and its upload to the chip, the baseline and planted move, each check's renders and read-backs and the reading of its figures, and the whole press. The three checks, their planted pairs, expectations, figures and order are as they were. What changed is where the work is done: each draw used to call `drawFrame`, which builds the photograph's pixels and a new picture code every time, about two dozen of each in a press; the press now opens one drawing surface, gives it the photograph once and draws every frame of every run through it with the same calls in the same order, and one row prints how many times the photograph was decoded, the picture code built and the photograph's pixels built, which the press is asked to make one each.

Additions of the plan of 5 November, step 298, put right the five findings the 2.71 reports queued, and change no check, band or expectation. The press keeps one mark on the page's clock and puts every stretch from the button to the done line under a named row, so the rows add up to the whole press, and one line prints that sum against the whole with the difference called "in no row"; the waits the press makes for the screen to draw are one row with a count, and while the page is hidden (a browser stops animation frames and throttles timers in a background tab) the press makes no such wait and the report says how many it skipped. The picture code's first draw is a row of its own, apart from the planted colour's, and each row made of three runs prints its first run's time beside its median. The drawing surface moved from `src/debug.ts` into `src/gpuexport.ts` as `openDrawing`, and `drawFrame` now opens it, draws once and closes it, so a change to the one reaches the other and the test page's picture checks draw through the code the export test draws through. The accessibility walk gained a section that presses the button and measures the test page with the press running, in both themes and both shapes. The three checks' expectations, planted pairs, figures and order are as on 2.71.

A fourth check on the page, the Separation check (the plan of 6 November 2026, step 305, on staging as 2.72, built for record 084's premise), has its own two buttons and is not one of the three above. It draws the photograph, the picked one (record 108) or else the practice file, through the same drawing surface with the swap on, no look and every control at its neutral, at three white points: the balance the editor opens at, a balance set from a neutral spot the reader taps or types, and a balance set from a foliage spot likewise, each set the way the editor's tap sets it. At each it reads the drawn pixels, thinned to about a million, counts the hues of the pixels above the band stage's saturation floor into 72 bins of five degrees, finds clusters by a stated rule (a run of bins between two valleys, a valley being a bin under one tenth of the smaller of its two nearest peaks, and a run under one percent of the pixels above the floor being no cluster), paints a class map, and turns the clusters in place twice, once to the film's two hues and once by plus 60 degrees for the rest. It runs once, since nothing in it is timed against a band, sets no band and no control, and prints every cluster's range, share and medians, the taps and the stage times in the copy. Under the container's software drawing only its structure is read; its pictures are read on the device.

The device pass: the owner opens the test page behind the version number on the iPad and on the PC, presses the button, and pastes the copied report back.
